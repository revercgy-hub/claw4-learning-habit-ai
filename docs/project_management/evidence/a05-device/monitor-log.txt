# A05-DEVICE D2 — 串口监控日志（monitor-log）

## 结论先行：本机 USB 控制台的可观测窗口只有每次复位后的前 ~1.4 秒
**这不是应用缺陷，而是本板 USB PHY 路由特性 + 主机侧句柄失效共同造成的观测限制。**证据链：

1. 候选 sdkconfig：`CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`、`CONFIG_ESP_CONSOLE_UART_NUM=-1`、
   `CONFIG_ESP_CONSOLE_SECONDARY_NONE=y` ⇒ **唯一控制台通道就是 USB-Serial/JTAG（COM7）**，
   没有第二路 UART 控制台。
2. 无干扰端口存在性测试（`_d2-presence-clean.txt`，esptool 复位后 10 s 内不持有任何串口句柄）：
   ```
   0.04s -> PRESENT  ports=[COM6,COM7,COM5,COM4]
   1.08s -> ABSENT   ports=[COM6]        <- USB-Serial/JTAG 掉线（重枚举）
   1.34s -> PRESENT  ports=[COM6,COM7]
   total_transitions=3                   <- 之后 8.6 s 稳定，无 boot loop
   ```
   ⇒ 每次复位后 ~1.1 s 有一次 **USB 重枚举毛刺**，约 260 ms 后 COM7 回来。
3. 主机侧句柄在该毛刺中失效；而**重新打开串口本身会再次复位芯片**
   （`_d2-presence.txt`：45 s 内 24 次复位；`_steady-attach.txt`：45 s 内 17 次 `rst:0x17`）。
   ⇒ 形成自持循环：开串口 → 复位 → 抓 ~1.4 s → 毛刺 → 句柄失效 → 再开 → 再复位 …
4. 因此**从主机侧只能稳定观测到每次运行的前 ~1.4 s**。

每一次都能抓到**完整且可复现**的启动前段，并且最后一次抓到了应用自身的第一条日志：
```
I (1447) METALIO_CLAW_4: LCD hardware reset done (GPIO 3).
```
⇒ 应用确实越过了 `main_task: Calling app_main()`，进入 `Board::GetDisplay()` 的 LCD 硬件复位阶段。
（该行在流里出现在 ROM banner 之前，是两次运行交叠的流序，不是时间倒置。）

  **无法从 bootloader 日志读 "Loaded app from partition at offset 0x…"**；启动槽位结论由 D0 的
  otadata 静态推理承担（见 otadata-decoded.txt）。

## 追加：配网 + 掉电上电后的第 5 次抓取（A05_DEVICE_BOOT_005.log，14:38，dur=50 s）
在**已配网、已拔插上电**的状态下再抓 50 s，结果与 001–004 结构性一致：

```
size = 1852 B      rst:0x 命中 = 0（本次复用已打开句柄做 RTS 复位，未捕获 ROM banner）
main_task: Calling app_main() 出现 1 次，且为最后一行
METALIO_CLAW_4 = 0   WIFI/wifi/ssid/Connecting/esp_netif = 0   got ip = 0
panic / Guru / abort / assert = 0
```
⇒ 再次证实：**主机侧观测窗口仍是每次运行的前 ~1.4 s**，`app_main()` 之后的 Wi-Fi/LVGL/音频/
Learning 初始化行**本轮仍然拿不到**；这不是应用静默，而是控制台通道在应用初始化 USB PHY 时掉线
（证据见本文件开头第 2 条与 `_d2-presence-clean.txt`）。

**补偿手段（本轮新增，见 network-smoke.txt / nvs-persistence.txt）**：改用 NVS 侧信道观测，
用 IDF 官方 `nvs_tool.py` + 自写 `nvs_diff.py` / `nvs_event_delta.py` 证明
① 配网凭据落盘并跨掉电保持；② 至少两次完整的 OTA HTTPS 往返（`mqtt:username` 由服务端响应驱动）；
③ 学习运行时在配网后新增 4 个事件 id + 1 个会话 id 并落盘。三者共同构成"应用健康且联网"的证据链。
