## 2. 更正一：`No AP found` 不是射频故障

三轮启动日志稳定出现：

```text
I (9599) WifiStation: Scanning all channels
I (12057) WifiStation: No AP found, next scan in 10 seconds
```

我一度把它读成"C5 扫不到任何 AP"。**读源码后确认这是误读。**

`managed_components/78__esp-wifi-connect/wifi_station.cc:227-275` 的
`HandleScanResult()`：先取全部 `ap_num` 条扫描结果，再用 `SsidManager` 里**已保存的
SSID 列表**做匹配；只有当 `connect_queue_` 为空（即**没有任何扫描结果匹配已保存 SSID**）
时才打印 `No AP found`。这个字符串与"扫到 0 个 AP"并不能区分。

而 `main/boards/common/wifi_board.cc:100-115` 的 `TryWifiConnect()` 决定了走哪条分支：

```cpp
bool have_ssid = !ssid_manager.GetSsidList().empty();
if (have_ssid) {
    ESP_LOGI(TAG, "Starting WiFi connection attempt");   // ← 日志里出现的就是这一条
    ...
}
```

日志里有 `I (8677) WifiBoard: Starting WiFi connection attempt`，所以 **`have_ssid == true`**：
设备的 NVS（原厂保留、未被 V6 刷写）里**存着旧 SSID**，而那个 AP 不在当前环境里。
于是扫描每轮都返回"无匹配"。

**结论**：这是"设备处于未配网状态、却带着旧凭据"的预期行为，不是 C5 硬件或驱动故障。
`NETWORK_EVENT=0` 也印证了这点 —— `board.h:20-33` 的枚举第 0 项是 `Scanning`，即板子只是停在扫描态。

### 真正可执行的下一步（零改码）

`main/boards/common/wifi_board.cc:27` 定义 `CONNECT_TIMEOUT_SEC = 60`，
`sdkconfig:1395` 有 `CONFIG_USE_HOTSPOT_WIFI_PROVISIONING=y`。也就是：

> 开机后等满 **60 秒**，`OnWifiConnectTimeout()` 会触发 → `StartWifiConfigMode()` →
> 设备开热点，进入配网模式。

而我们四轮取证最长只观察到 **45 秒**（round 4 实际 29.6 s），**从来没有跑到超时点**，
所以也从没进过配网、从没联过网。这解释了 `NETWORK_IP=NOT_VERIFIED` 的全部原因。

**建议的验证动作（不需要重刷固件）**：让设备静置 ≥70 秒并抓串口，出现
`WiFi config mode entered` 后用手机连设备热点配网，再确认出现
`Connected to WiFi: <ssid>` 与 `NETWORK_EVENT=2`（`Connected`）。

附带一条独立的小问题（不影响功能）：`E (6005) system_api: 0 mac type is incorrect (not found)`
出现在 6.0 s，而 `RPC_WRAP: Coprocessor Boot-up` 在 8.5 s —— 应用在从机就绪之前就去取
WiFi MAC 了。这是时序问题，不是错误配置；但它会让设备身份字符串拿到非预期值，
M1 接后端时如果依赖 MAC 生成设备 ID，需要先处理。

## 3. 更正二：`wake=1` 不是"检测到唤醒"

`boot-m0-02/03.txt` 的 HEALTH 行里 `wake=1` 出现多次，
容易被读成"唤醒词已触发过"。查 `m0_diagnostics.cc:68-73`：

```cpp
ESP_LOGI("V6M0", "HEALTH free=%u psram=%u wake=%d taps=%u",
         ..., audio.IsWakeWordRunning(), taps.load());
```

`wake=` 打印的是 `IsWakeWordRunning()`，即**唤醒引擎是否在运行**（armed），
是一个恒定状态位，不是事件计数。真正的正事件只有
`m0_diagnostics.cc:35` 注册的 `WAKE_DETECTED (local only)`，
而它在四轮全部日志中**出现 0 次**。

**结论**：唤醒词 = 从未验证。`wn9_nihaoxiaozhi_tts` 模型加载成功、
AFE 流水线 `|AEC(FD_LOW_COST, NLP_VERY_AGGRESSIVE)| -> |VAD(WebRTC)| -> |WakeNet(...)|`
构建成功，这些只能证明"引擎跑起来了"。

> **§3.1 后续补充（2026-09-22 11:35，修正我自己初版的措辞）**
>
> 初版把 `wake=` 说成"恒定状态位"。读全因果链后更精确的说法是：
> `audio_service.cc:686` 在 `EnableWakeWordDetection(true)` 成功时**置位**，
> `audio_service.cc:97` 在**检测到唤醒时清位**。也就是说：
>
> - `wake=1` 持续 = 引擎 armed **且**从未有过检测 ⇒ **是"零检测"的旁证**；
> - 任何一次 `wake=0` 的 HEALTH 采样都意味着刚发生过一次检测。
>
> 全部捕获的约 30 个 HEALTH 采样**无一出现过 `wake=0`**，与 `WAKE_DETECTED` 计数
> 为 0 相互印证。**方向不能反**：`wake=1` 永远不能当作"检测到了"的证据。
>
> 同时确认取证口本身没有接错：`SetCallbacks()` 只是 `callbacks_ = callbacks`
> （`audio_service.cc:762`），而唤醒 lambda 捕获 `this` 在**调用时**才读 `callbacks_`
> （`audio_service.cc:96-101`），所以在 `Initialize()`/`Start()` 之后再注册回调是有效的。
> **`WAKE_DETECTED` 未出现是真实结果，不是插桩假阴性。**
>
> 另注：`Enable/Disabling wake word detection` 是 `ESP_LOGD`（`audio_service.cc:662`），
> 默认日志级别不打印，所以看不到 record 循环里 arm/disarm 的切换 —— 这是正常的。

> 顺带：本机唤醒词模型在独立 `srmodels` 分区（`0x10f000`），当前 V6 已刷入
> `srmodels.bin`（291,042 B）。模型名是 `wn9_nihaoxiaozhi_tts`，与设备实际可用唤醒词一致，
> 这一点比 V5.3 时期（分区未更新导致"嗨钛灵"与配置不符）是明确改善。

## 4. 音频：用户确认回环成功，但别把它读成"音质通过"

`m0_diagnostics.cc:58-66` 的按钮流程是：置 `EnableAudioTesting(true)` → 等 3000 ms →
关闭 → 打印 `playback queued`。查 `main/audio/audio_service.cc:734-749`：
开启时麦克风采集进入 `audio_testing_queue_`（**不经云端、不送 ASR**），
关闭时把该队列 `swap` 进 `audio_decode_queue_` 走正常播放通路。

所以这一操作 = **本地采集 3 秒 + 扬声器回放**，是一条完整的
"麦克风 → 内存 → 扬声器"闭环，用户已确认成功。

这条证据成立的范围：

- ✅ 麦克风采集通路可用
- ✅ 扬声器播放通路可用
- ✅ 触摸 → 业务逻辑 → 音频 的联动可用
- ❌ 不能推出：麦克风信噪比/灵敏度可用
- ❌ 不能推出：扬声器音量与失真可用
- ❌ 不能推出：AEC 回声抑制效果可用（诊断流程里没有对讲场景）
- ❌ 不能推出：唤醒词唤醒率可用（`WAKE_DETECTED` 为 0）

## 14. 唤醒词实测：查出一个自恢复缺陷，并修正我上一轮的两处说法

2026-09-22 12:08。两轮实测 + 源码追查。

### 14.1 实测结果

| 轮次 | 动作 | 观测 | 结果 |
| --- | --- | --- | --- |
| 第 1 轮 | 未复位，直接抓 105 s | `wake` **全程为 0**，`WAKE_DETECTED` = 0，`taps` = 0 | 见 §14.2 |
| 第 2 轮 | 复位后抓 105 s（60 + 45 s） | `wake` **全程为 1**，`WAKE_DETECTED` = 0 | 未触发 |

### 14.2 发现：首次检测后唤醒检测器**不会自恢复**（M0 诊断固件的缺陷）

读 `main/audio/audio_service.cc` 的音频输入任务：

```cpp
EventBits_t bits = xEventGroupWaitBits(... WAKE_WORD_RUNNING | AUDIO_PROCESSOR_RUNNING ...);
if (bits & (AS_EVENT_WAKE_WORD_RUNNING | AS_EVENT_AUDIO_PROCESSOR_RUNNING)) {
    audio_engine_->Feed(std::move(data));      // ← 只有位被置位时才喂音频
}
```

而唤醒回调在**检测到唤醒时清掉这个位**（`audio_service.cc:97`）。
`m0_diagnostics.cc` 的空闲循环只在**按屏幕按钮**走 record 分支时才
`EnableWakeWordDetection(true)` 重新置位。

⇒ 后果链：**一次检测 → 位清零 → 音频不再喂引擎 → 之后永远检测不到 → 直到按键或重启。**

**这不是上游缺陷，是 M0 诊断脚手架没处理"检测已发生"这个状态。**
M0 的证据因此不能用来判断"唤醒率"，只能判断"能否触发"。

### 14.3 第 1 轮的 `wake=0` 说明：**此前确实发生过一次检测**

本轮开机后 `taps` 恒为 0、`Start()` 只调用过一次，而能把该位清零的代码只有两条：
`audio_service.cc:97`（检测到唤醒）与 `:665/671/676`（重新使能失败，需先有一次 record 循环）。
⇒ **只剩 `:97`，即 11:25:39 至 12:08:36 之间发生过一次检测**，但那条
`WAKE_DETECTED` 落在我没有抓串口的窗口里。

**时间线吻合**：11:24 我请用户说唤醒词未成；11:30 用户询问"能否用响指替代"
⇒ 用户很可能在那前后**打了响指**。

### 14.4 修正我一处说过头的话

我在 11:24 说过"**响指不会触发** WakeNet"。§14.3 的锁存证据显示
**宽带瞬态确实可能造成误触发**。准确的说法应当是：

> 响指**不在 WakeNet 的目标可分空间内，因此不可靠**——不能当作唤醒词的替代刺激。
> 但它**并非绝对不触发**：本次锁存证据指向它造成了一次误触发。

这个区别重要：**误触发是可用性噪音，不是功能可用性证据。**

### 14.5 第 2 轮 0 检测的待澄清项

复位后 105 秒（`wake` 全程为 1，说明检测器**处于工作状态**）但没有一次检测。
在给出结论前必须先澄清刺激条件，否则会把"用户没说话/太远/太轻"写成"功能失效"：

- 距离设备多远？音量如何？
- 是否对着麦克风孔方向？

若刺激条件正常仍为 0，则下一步按 §14.6 收敛。

### 14.6 建议的下一步（按顺序）

## 12. 补充二：配网已执行，根因落在上游重连路径（2026-09-22 10:37）

用户完成配网后我做了只读取证。**结论与 §11.3 的预期不同：配网本身成功了，但重连失败，
且根因是上游组件不支持隐藏 SSID 的重连。** 完整证据见 `docs/v6/V6_M0_NETWORK_PROBE.md` §8。

### 12.1 三个独立证据位

| 证据 | 方法 | 结果 |
| --- | --- | --- |
| 凭据已落盘 | `esptool read_flash 0x3c000 0xd2000` 回读 NVS，与刷机前备份同区间**逐字节比对** | 变化 144 字节 / 2 个脏页；新增 `ssid`、`channel` 键与 SSID 字面量（10 位纯 ASCII，无中文无空格） |
| C5 关联能力正常 | 读 `WifiConfigurationAp` 保存流程源码 | `TryConnect` **成功才** `Save()`；保存的 `channel` 来自 `last_connected_channel_` ⇒ **配网时确实关联成功过** |
| 目标 AP 不广播 SSID | 主机侧 `netsh wlan show networks mode=bssid` 无线勘测 | 该 SSID **不在可见列表**；环境中唯一的空名隐藏 AP（`f4:79:60:xx`，三射频）其 **2.4 GHz 射频频道 = 11**，与 NVS 保存的 channel **完全一致** |

### 12.2 代码级根因

`managed_components/78__esp-wifi-connect/wifi_station.cc`：

- `StartConnect()` 只有两个调用点（`HandleScanResult()` 第 277 行、`WifiEventHandler` 第 438 行），
  **不存在"按已保存 SSID 直连"的入口**；
- `HandleScanResult()` 用 `strcmp(ap_record.ssid, item.ssid)` 匹配，隐藏 SSID 的
  `ap_record.ssid` 是空串，**永远匹配不上**。

而配网路径（`WifiConfigurationAp::TryConnect`）把 ssid/password 直接写进
`wifi_config.sta` 连接，**不依赖先扫到**。这就是"配网连得上、重连连不上"的全部原因。

**定性：这不是设备缺陷，是上游组件对隐藏 SSID 重连的功能缺口。**

### 12.3 对 M0/M1 判定的影响

- `网络 / IP` 在矩阵里**保持 `NOT_VERIFIED`**。§12.1 的隐藏 SSID 结论是
  "主机侧勘测 + NVS 信道互证"的强推论，**未直接读到 C5 自己的扫描列表**，故不升级状态。
- **M1 的网络前提比原先估计更重**：不是"再配一次网"，而是必须先落地 §12.5 的修复，
  或联调期改用广播 SSID 的 AP。当前 AP 在现有上游组件下**永远连不上**。
- C5 射频、SDIO 链路、关联能力三项由此**从"未验证"变为"已证伪为无问题"**，
  但矩阵不新增"射频可用"行 —— 因为唯一支撑它的关联成功发生在**配网进程内**，
  不是应用自身的连接路径。该证据写在本节，不写进验收矩阵。

### 12.4 建议 Codex 复检的新增重点

1. §12.2 的代码级根因是否成立（`StartConnect` 调用点是否确实只有两处）；
2. §12.5 的方案选择；
3. `78__esp-wifi-connect` 是 **managed component**，任何改动都要按项目规则
   记录并保留原实现与上游比对基线。

### 12.5 修复方向（供 Codex 决策，本报告不实施）

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A** | 扫描连续 N 轮无匹配后，回退为"用 `SsidManager` 第一条已保存凭据直连"，即照抄配网的成功路径 | **推荐**。改动小、与配网路径一致、对可见 SSID 零影响 |
| B | 先查上游新版 `78__esp-wifi-connect` 是否已修，能升则升 | **优先查**，可能零自研 |
| C | 应用层加"手动重连"入口 | 治标，每次开机仍需人工操作 |
