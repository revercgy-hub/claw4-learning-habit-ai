The 60-second USB-reset boot log shows ROM/app ELF prefix `33955b7af`, `ota_0` running, Wi-Fi `505` connected, then `EspTcp: Resolved 192.168.3.100 -> 192.168.3.100` and `HttpClient: Established new connection to 192.168.3.100:7443 protocol=http` at device uptime 11.858 s. OTA check closed normally and activation reached idle. AFE initialized with microphone plus playback-reference channels and a WakeNet model; these setup messages do **not** prove AEC effect or wake reliability. No `api.tenclass.net` or MQTT connection is logged in the 60-second boot capture. No WebSocket connection to NAS `192.168.3.100:7444/xiaozhi/v1/` is logged either. The firmware opens that channel lazily after Wake or a manual chat trigger. Source review found no manual chat callback in this Claw4 board: its power key only emits diagnostics, and its board touch initialization has no chat handler.

Astra allowed one wake-word-only endpoint probe, separate from a complete Voice round. Two separate 60-second passive serial captures were made without reset. The first main segment spans device uptime about 263.370–322.664 s; the second spans about 375.929–435.224 s, leaving an uncovered gap of about 53 s. Each capture opens with a stale serial fragment, which is not used as a session marker. The exact time of the user-reported single wake-word attempt relative to these windows and gap is unknown. Neither captured main segment has a Wake, WebSocket, MQTT, external endpoint, crash or reboot marker. This is **not** evidence that Wake failed under a confirmed in-window controlled stimulus. No second user wake attempt was requested. Since the live WebSocket target remains unobserved, the endpoint gate stays closed and no Speech→ASR→LLM→TTS→Playback test was requested.
