# S-05 M1 Voice device preflight: blocked before speech

Status: **BLOCKED_ENDPOINT_MISMATCH** (2026-09-25). The reviewed Candidate was written only to the live `ota_0` application address and its readback passed. The first bound USB-reset boot then contacted the external XiaoZhi OTA service and connected to its MQTT broker instead of the required private NAS. S-05 stopped before asking for, capturing, or sending any speech. Preflight rounds executed: **0**. This report does not establish M1 PASS or change `M0=CHANGES_REQUIRED`.

## Effective endpoint mismatch

The USB-reset capture has ROM/app ELF prefix `0fcef5675`, matching the frozen ELF, and logs `Running partition: ota_0` and Wi-Fi connection to `505`. At 13.374 s, 23.616 s, and 27.404 s it records HTTPS connections to `api.tenclass.net:443`. At 27.654 s it attempts MQTT `api.tenclass.net:8883`; at 28.260 s the MQTT connection succeeds. There is no observed request to `192.168.3.100:7443` or WebSocket connection to `192.168.3.100:7444` in the 45-second capture. An activation code appears in the private raw log and is intentionally omitted here.

The frozen `sdkconfig` and generated `sdkconfig.h` both set `CONFIG_OTA_URL` to `http://192.168.3.100:7443/xiaozhi/ota/`. However, staged upstream `main/ota.cc` `GetCheckVersionUrl()` first reads `Settings("wifi", false).GetString("ota_url")` and uses the compiled URL only when that stored value is empty. The boot evidence is consistent with a persisted URL override, but S-05 did not read NVS, so the exact stored value is **inferred, not verified**. The OTA response can populate `mqtt`/`websocket` settings; `Application::InitializeProtocol()` chooses MQTT when OTA has MQTT config, and the captured live MQTT connection proves the active protocol reached the external broker. This is more than an OTA-only fallback. The exact network contents, credentials and activation response were not copied to Git.
