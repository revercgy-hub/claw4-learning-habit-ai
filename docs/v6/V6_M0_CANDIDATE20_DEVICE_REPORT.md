## Provisioning read-only audit

The built configuration enables hotspot provisioning (`CONFIG_USE_HOTSPOT_WIFI_PROVISIONING=y`). `WifiBoard::StartNetwork()` is called at M0 startup. It tries stored networks; no saved network, or a startup connection timeout of about 60 seconds, enters `StartWifiConfigMode()` and `WifiManager::StartConfigAp()`. The hotspot is `Xiaozhi-*`, with portal at `http://192.168.4.1`. On successful connection, its handler persists the entered SSID/password through `Save()`/NVS. The M0 board's Record/Playback and diagnostic power-key handlers do not call `EnterWifiConfigMode()`. Disabling an already connected AP alone is not a demonstrated portal trigger. This is a code-path finding, not a Candidate20 device result; no provisioning or NVS action was performed in this audit. The password for target SSID `505` must be entered by the operator locally, never in logs, Git, or chat.

To resume formal device evidence, first capture a new boot and verify the full ELF anchor against Candidate20, then bind subsequent captures to that new session with immutable hashes. A `--reset` serial capture can anchor a USB-reset session, but cannot close the genuine cold-boot requirement. The old saved AP would need to be unavailable during a fresh startup for the observed timeout path to open the portal, subject to the owner's separate direction. Then test target SSID `505` connection and a controlled AP off/on cycle in bounded, identity-bound sessions. Do not repeat already bound boot/C5/SD/touch observations. No M0 PASS is claimed.
