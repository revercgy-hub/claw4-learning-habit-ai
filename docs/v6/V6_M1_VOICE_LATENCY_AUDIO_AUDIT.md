## Separate NAS latency and device audio decisions

**NAS latency:** The inspected production Ollama provider calls OpenAI-compatible `chat.completions.create(model, messages, stream=True)` with a `/no_think` prompt addition but does not pass native `think`, `reasoning_effort`, request timeout or `max_tokens` ([source lines 27–48](E:/v6/nas-latency-20261020-01/upstream-ollama-v096.py#L27); its tools call at lines 95–118 also omits those options). The missing native reasoning control is a CODE finding; the prompt suffix is not proof of effective model control. In [Ollama v0.30.7's OpenAI compatibility code](https://github.com/ollama/ollama/blob/v0.30.7/openai/openai.go#L591-L617), `reasoning_effort="none"` maps to native `Think=false`. Root's first native comparison failed (exit `1`, null result); it was superseded for comparison by two successful **synthetic HOST probes**: native `think=false` took 5.073 s to first content, 5.107 s total, including 4.896 s model load, with zero thinking characters and the expected result; OpenAI compatibility with `reasoning_effort="none"` on the warm model took 0.307 s to first content, 0.342 s total, also zero reasoning characters and the expected result. These different cold/warm calls are **not a controlled A/B** against current production. The earlier production-provider synthetic call exited `124` at a 90 s outer timeout; whether it emitted a first token is unknown. The observations make reasoning control and provider timing a bounded repair target, but do not prove that this parameter caused all, or any fixed fraction, of the DEVICE session's 55.431 s to matching TTS *text*. Safe NAS events show new LLM activity after each of three interrupts, with only wall-clock seconds and no token/audio timestamps. Server inference, interruption/retry and downstream playback delay remain unseparated. Neither 403 nor MP3 decode failure is observed in the later service window.

**Audio/session lifecycle:** CODE establishes a realtime capture path during speaking, software TX reference injection, local decoder reset on speaking entry, and a state-dependent incoming audio gate. DEVICE establishes speaking/listening transitions, extra ASR markers and aggregate reference underflow during playback windows. It does **not** establish which uplink frames caused an ASR, reference-to-mic acoustic alignment, AEC attenuation, TTS packet delivery, actual speaker output, near-end behavior during playback, or successful next-wake recovery. The three extra ASRs therefore cannot be classified as acoustic echo or as intended barge-in. A late correct TTS text marker cannot override the operator's slow/incorrect heard-response report.

## Actual staged audio and state semantics

The S15 candidate manifest records staged `sdkconfig` SHA256 `56d0f7239a7e3c5ccb688293c5f1aea3dff957daade95baf8c2569bdc8b0d712`; read-only hashing of the staged file matched. Its lines 1352, 1376, 1380–1386, 1384 and 1497 select Claw4, AFE wake, wake-word-data upload, audio processor and **device AEC**, leave **server AEC** and wake detection while listening disabled, and select the repaired wake model. Thus this is a **full-duplex I2S / real-time uplink configuration**, not a half-duplex or server-AEC configuration. It is not an AEC effectiveness result.

- `main/boards/metalio/claw4-learning-v6/claw4_audio.cc:11–35,57–65,77–126,218–266` sets `duplex_=true`, two interleaved AFE input channels, and `input_reference_=true`. The physical R slot was silent in Candidate20, so the second AFE slot is overwritten with accepted post-volume TX samples from a bounded software queue. The code labels its alignment uncalibrated; actual speaker acoustic delay is unmeasured. `TX_REFERENCE` reports that source and queue counts (`:187–197`). Staged board and AFE hashes match the candidate manifest: board `c0ce2b3b868f821d6f9c2865eb98aa901ebd2cabeab98693a47d5ade166a18c3`; AFE `1207713347812768091be7572eaf55cc58e147c856099c5c4dffae6a5b48d8a5`.
- `main/audio/engines/afe_audio_engine.cc:174–245,389–395,490–497,536–589` configures `MR` full-duplex AFE with low-cost AEC; AEC is enabled when wake detection is on, or while voice processing is on with device AEC enabled. `main/audio/audio_service.h:201–206` defaults that flag true for this Kconfig. The AFE feeds output to the uplink callback while voice processing is enabled (`afe_audio_engine.cc:622–650`; `audio_service.cc:87–89`). Reference entry into AFE and configured AEC do not establish echo removal.
- A sanitized counter-only scan of the private capture found 585 `TX_REFERENCE` windows, sum overflow=0, stale_writes=0, discarded=0, underflow=18,336 samples; only 13 windows reported active reference. Underflow occurred around 435–437, 446–448 and 494–501 seconds, overlapping known playback periods. These are queue availability/alignment warning signals, not a calibrated per-frame AEC failure measurement: the counter also advances across playback tail/idle, and logs aggregate about once per second. No gain or delay value follows from this scan.
- `main/application.cc:26–34,1019–1047,1063–1089,1180–1182` makes device AEC choose `kListeningModeRealtime`. On entering speaking, voice processing is disabled only when mode is **not** realtime. Thus real-time uplink can continue during playback. Wake detection is disabled in listening by current Kconfig and on speaking entry it is not separately re-enabled in realtime. This session's later return to listening does not demonstrate **next wake** recovery in idle.
- Incoming audio packets are accepted only in speaking (`application.cc:552–556`). A server TTS start schedules `aborted_=false` and speaking; stop returns to listening unless manual mode (`:615–635`). Wake in speaking/listening sends abort, drains the uplink queue, and moves to listening or sends a fresh start (`:889–919`); `AbortSpeaking` sets `aborted_` and sends protocol abort (`:1167–1173`). `ResetDecoder` clears local decode/playback queues (`audio_service.cc:798–810`), but the observed ASR/interruption sequence cannot be attributed to a specific queued packet from these logs. `CONFIG_WAKE_WORD_DETECTION_IN_LISTENING` is off, so claiming playback barge-in by wake word from these extra ASRs would be unsupported.

1. Root's separate NAS owner may make the smallest provider-only change to pass native reasoning control through the compatible API, with a bounded request and an explicit first-token measurement. Verify a synthetic production-provider call before/after under comparable warm/cold state, including completion, output class, error/timeout and service identity; preserve the prior 90 s timeout as censored evidence. Do not change firmware, AEC mode or ADR from this finding. Split ASR final → LLM first token, LLM first token → TTS first audio, first audio → device playback, and interruption/retry time. Do not equate a TTS sentence text marker with first audio or heard answer.
2. Keep the current candidate and service identity fixed for one **diagnostic preflight pair** under the root owner: the same short synthetic question once with a time-stamped near-end stimulus and once with playback only. Record privately device state, uplink start/stop, TTS text/audio start/end, per-window reference active/underflow, server ASR-final/LLM first token/TTS first audio, interrupt reason, and operator-observed audible output. Publish only counts, durations, hashes, and classifications. Stop if identity changes, a capture lacks a valid session binding, a service fault recurs, or the same unexplained interrupt appears again; preserve the evidence and diagnose before another run.
3. If playback-only produces ASR/interrupts, isolate source with time-aligned private mic/reference/playback envelopes and bounded AEC state telemetry. Then review reference availability and session queue lifetime before changing gain/delay. If near-end stimulus is responsible, review the product's barge-in policy and server interrupt handling instead. Any change to realtime/half-duplex, wake ownership, or server protocol is a public session contract decision for the root owner under ADR-001; this S-18 report makes no such change.
4. Acceptance of the subsequent preflight requires an audible correct response, bounded time, no unexplained extra ASR/interrupt, playback-period near-end behavior explicitly tested, and an independent next-wake test. AEC effectiveness needs controlled near-end plus playback evidence; even that preflight would not count toward formal 20 rounds until the root freezes a valid candidate and starts them.
